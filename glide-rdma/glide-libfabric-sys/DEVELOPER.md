# Developer Guide

This crate is a vendored copy of `bindings/rust` from
[ofiwg/libfabric](https://github.com/ofiwg/libfabric) at revision
`6953579a5035`, published upstream as
[`ofi-libfabric-sys`](https://crates.io/crates/ofi-libfabric-sys). It is a
lightweight binding generated by bindgen, with no abstraction on top of the
generated code aside from `wrapper.[ch]`, which lets the `static inline`
libfabric functions be bound.

This crate is only usable together with `glide-rdma`. See
[Differences from upstream](#differences-from-upstream).

## Build

```bash
# Build. Needs a C compiler.
cargo build

# Regenerate `src/bindings.rs` from the vendored headers. Needs libclang.
cargo build --features regenerate-bindings
```

A program built from this crate alone does not link, because `glide-rdma`
defines the libfabric functions that the bindings call.

## Files

- `build.rs`: The build script. It compiles `wrapper.c` and copies
  `src/bindings.rs` into `OUT_DIR`, fixing the link names for the target OS.
  With `regenerate-bindings`, it runs bindgen first.
- `src/bindings.rs`: The generated bindings, kept in the tree.
- `src/lib.rs`: Exports the generated bindings under the `bindgen` namespace.
- `wrapper.[ch]`: Wrapper source files that call the `static inline` functions.
  This way, an isolated translation unit is made for each `static inline`
  function, which the Rust bindings can link against.
- `include/`: The vendored libfabric public headers.
- `COPYING`: libfabric's license, kept word for word from upstream.

## Differences from upstream

It differs from upstream in seven ways, the first four so that a build of GLIDE
does not need libfabric installed and a shipped binary does not hard-link
libfabric on the runtime machine.

1. **Crate metadata is inlined** rather than inherited from libfabric's Cargo
   workspace, which is not vendored with it.

1. **libfabric is never linked.** Upstream emits `cargo:rustc-link-lib=fabric`
   which requires the runtime host to have libfabric even if they weren't
   going to use the `glide-rdma` feature. Here, `glide-rdma` defines libfabric
   symbols and resolves them at runtime by the dlopen shim in `glide-rdma`.
   Since nothing is linked, the manifest also has no `links = "libfabric"`
   key.

   Those definitions are named `glide_fi_getinfo` and so on, not libfabric's own
   names, so that they cannot clash with a real libfabric that something else in
   the same process has loaded. The Rust bindings keep libfabric's names but link
   to the prefixed symbols and `wrapper.c` renames its calls to match. The list
   of renamed functions is `SHIMMED` in `build.rs` and the same list is in
   `wrapper.c`.

1. **libfabric's public headers are vendored under `include/`.** Upstream builds
   against whatever `pkg-config` finds on the build machine.

1. **The bindgen output is generated once and kept as `src/bindings.rs`.**
   One consequence to know about: some of the constants bindgen copies out are
   the build machine's, not the target's. The `FI_E*` codes below 256 are
   defined as the platform's own `errno` values, which differ (`FI_ENODATA` is
   61 on Linux and 96 on macOS), so the checked-in file carries whichever set
   belonged to the machine that last ran bindgen. Do not compare a libfabric
   return code against these; take the value from `libc` instead, which follows
   the target. libfabric's own codes, from 256 up (`FI_ETOOSMALL` and later),
   are the same everywhere.

1. **The `cargo:warning` lines listing the include paths are removed.** Upstream
   prints them on every build, and cargo repeats them for everyone who depends on
   the crate. They read as debug output left behind. For the same reason,
   `wrapper.c` has no wrappers for the functions libfabric marks deprecated, such
   as `fi_poll` and `fi_rx_size_left`. Each one printed a compiler warning on
   every build, and `glide-rdma` calls none of them.

1. **Upstream's `asan` feature and unit tests are removed.** The bindings are
   exercised through `glide-rdma`'s tests instead.

1. **The crate is renamed from `ofi-libfabric-sys` to `glide-libfabric-sys`.**
   Upstream already publishes `ofi-libfabric-sys` on crates.io, and this copy
   is published too, because `glide-core` depends on `glide-rdma` (behind its
   `rdma` feature). Code imports it as `glide_libfabric_sys`.

Together, (3) and (4) mean a release builder needs neither `libfabric-dev` nor
`libclang`.

## Regenerating the bindings

After changing anything under `include/`:

```bash
cargo build --features regenerate-bindings   # needs libclang
```

This rewrites `src/bindings.rs` in place. Commit the result. The API version it
describes — `FI_MAJOR_VERSION` and `FI_MINOR_VERSION` near the top — is the
version `glide-rdma` will refuse to run against anything older than, so a header
bump is a deliberate change to what the client supports.
