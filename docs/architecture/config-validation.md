# Client Configuration Validation
Validation is distributed rather than centralized. Each wrapper validates selected user-facing invariants, while `glide-core` handles shared semantic and connection-dependent validation.

| Client | Client-side validation | Boundary/conversion validation | Important gaps or deferred checks |
|---|---|---|---|
| **Python** | Primarily in `python/glide-shared/glide_shared/config.py`. Constructors/value objects validate credentials exclusivity and IAM username, AZ requirements, library metadata, circuit-breaker ranges, compression minimums, reconciliation interval, and mTLS pairing/exclusivity. `_create_a_protobuf_conn_request` validates TLS combinations and Pub/Sub requirements such as RESP3. | Generated protobuf assignments enforce protobuf scalar types/ranges. `ffi/src/lib.rs` rejects malformed protobuf bytes. `glide-core/src/client/types.rs` then normalizes zero and missing values. | `NodeAddress`, backoff values, database ID, most timeouts, inflight limits, and periodic intervals are not comprehensively checked in constructors. Some invalid values fail only during protobuf assignment or core connection. |
| **Go** | Builders in `go/config/config.go` mostly just store values. Validation is concentrated in `baseClientConfiguration.toProtobuf`, `ClientConfiguration.ToProtobuf`, and `ClusterClientConfiguration.ToProtobuf`: duration bounds, AZ requirements, library metadata, TLS combinations, compression, circuit breaker, and standalone read-only/AZ incompatibility. IAM and mTLS constructors also validate selected invariants. | `proto.Marshal` checks encodability, not semantics. Shared `glide-ffi` rejects malformed protobuf; core conversion normalizes/defaults. | Negative signed database, port, and backoff values can be cast to unsigned protobuf fields. Empty hosts, zero periodic intervals, and many limits are not comprehensively rejected. |
| **Java** | Public config classes and Lombok builders provide type/default constraints. Explicit checks are spread across `BaseClientConfiguration`, `AdvancedBaseClientConfiguration`, `TlsAdvancedConfiguration`, and `BaseClient`: library metadata, TLS/mTLS shape, positive reconciliation intervals, credentials, and Pub/Sub/RESP3. `java/client/src/main/java/glide/managers/ConnectionManager.java` validates circuit-breaker ranges while building the protobuf. | `ConnectionManager` serializes `ConnectionRequest`; JNI parses it and converts it to the core request. JNI protobuf parsing validates wire format only. | No comprehensive runtime checks were found for ordinary address ports, request timeout, database ID, inflight limit, retry values, periodic interval, or recovery queue size. JNI currently reduces many native creation failures to a zero handle and Java surfaces a fairly generic creation error. |
| **Node.js** | TypeScript interfaces provide compile-time structure. Runtime checks are mainly in `node/src/BaseClient.ts`: IAM username, AZ requirements, circuit-breaker values, compression, Pub/Sub/RESP3, and TLS/mTLS. TLS helpers explicitly reject empty material and invalid or overflowing reload intervals. Library metadata is validated by `ClientLibraryNameResolver`. | Protobufjs creates and encodes `ConnectionRequest`; N-API parses it and converts it to core types. N-API reports malformed protobuf and generally preserves core error text. | TypeScript types do not protect untyped JavaScript callers. General port, database, request timeout, inflight, retry, periodic, and recovery values are not comprehensively runtime-validated; protobufjs may coerce numeric values. |
| **C#** | This has the strongest front-end validation of the clients inspected. `valkey-glide-csharp/sources/Valkey.Glide/ConnectionConfiguration.cs` and related value objects validate positive/bounded durations, nonzero inflight limits, AZ/read strategy combinations, credentials, TLS prerequisites, certificate size/content, reload intervals, compression, cache, and most circuit-breaker values. Types such as `ushort`, `uint`, and enums rule out many ordinary invalid inputs. | `ToFfi()` and `FFI.structs.cs` mainly marshal validated values into sequential C layouts. The custom `glide_rs` bridge in `rust/src/ffi.rs` validates recoverable text conversion such as UTF-8 and constructs core types directly. Pointer validity, struct layout, and enum discriminants are trusted ABI preconditions—not recoverable validation. | There is no final holistic `Build()` validation pass. Invalid enum casts or internal construction can bypass normal setters. The inspected circuit-breaker threshold check does not enforce the documented upper bound of `1.0`. |
| **PHP** | PHP arginfo and Zend parsing provide top-level type enforcement. Further checks occur in `valkey_glide.c` and `valkey_glide_cluster.c`: enum values, required/nonempty addresses, nonnegative database IDs, conflicting parameter styles, IAM username, TLS cross-field requirements, metadata, compression minimum, and selected cache fields. | `valkey_glide_core_commands.c` maps the local C configuration to protobuf-c and packs it. Packing checks encodability but is mainly mapping/defaulting. Shared `glide-ffi` parses the protobuf and delegates to core. | Nested PHP arrays are only partially validated; wrong nested values often receive defaults. Port and several integer fields lack checked range conversion. Nonpositive request timeout is defaulted rather than rejected, and cluster periodic-check values are not comprehensively validated. |
| **Ruby** | `valkey-glide-ruby/lib/valkey.rb` checks database nonnegativity, nonempty nodes, first-node host/port presence, timeout types/positivity, AZ requirements, retry values, and TLS file existence/readability. `lib/valkey/utils.rb` validates supplied URL syntax, scheme, host, and database path. | Ruby calls shared `create_client_from_uri`. `valkey-glide/ffi/src/lib.rs` performs substantial URI/JSON validation: valid URI/UTF-8, known JSON keys, top-level/nested types, protocol/read/TLS enum names, periodic-check shape, and similar checks. It then builds protobuf and enters the normal core path. | Only the first `nodes` entry is encoded into the URI. Port range is not explicitly checked. Some malformed Ruby values fail incidentally rather than through deliberate validation. Several JSON integer conversions accept zero or narrow values above `u32::MAX`. |
| **Rust** | Mostly enforced through types in `rust/src/config`: `u16` ports, unsigned limits, `Duration`, closed enums, and a paired `ClientIdentity`. URL constructors validate URL syntax and reject unsupported Unix sockets. Cluster `from_urls` requires at least one URL, consistent credentials/client name/database/TLS across seeds, and database 0. | There is no serialization boundary. `to_request()` directly constructs `glide_core::client::ConnectionRequest`; it mostly maps values rather than validating them. | There is no general `validate()` method. Direct builders accept empty address lists/hosts, port 0, zero timeouts and limits, empty AZ strings, unrestricted jitter percentages, empty certificate bytes, and negative standalone database IDs. Most failures therefore occur in core. |

## Shared validation applied after client-specific checks

| Layer | What it validates or normalizes |
|---|---|
| **Protobuf parser** | Rejects malformed or truncated wire data. It does **not** establish that a configuration is semantically valid. This applies to the shared FFI, JNI, and N-API paths. |
| **Protobuf-to-core conversion** | `glide-core/src/client/types.rs` primarily normalizes: zero timeouts/limits become absent, empty strings become `None`, missing values receive defaults later, and some unknown/invalid enum situations fall back or are omitted. It is not a comprehensive validator. |
| **`Client::new`** | `glide-core/src/client/mod.rs` validates the effective library name, creates and validates the compression manager, applies defaults, initializes common state, and bounds eager creation by the connection timeout. Some zero circuit-breaker fields become defaults rather than errors. |
| **Standalone creation** | `glide-core/src/client/standalone_client.rs` rejects empty addresses, read-only with AZ-affinity, and read-only with `DiscoverAll`; validates TLS/certificate combinations; connects to nodes; detects conflicting primaries; and requires an appropriate usable topology. |
| **Cluster creation** | Validates TLS/certificate pairing and material, delegates seed and builder checks to the cluster implementation, opens connections, validates authentication/topology, and rejects sharded Pub/Sub against engines older than 7.0. |
| **Server/connection setup** | Ultimately validates DNS/reachability, TLS handshake, credentials, database support/range, protocol compatibility, node roles, and actual cluster topology. |

A major timing distinction is `lazy_connect`: wrapper and immediate `Client::new` checks still run, but address, TLS material, authentication, topology, database support, and server capability validation are generally deferred until the first command.
